Jarvis theme · operations runbook

Upgrading Jarvis on a live site

Three install methods are in use across these servers, and the commands differ for each. Work out which route a site is on, run that route, then run the shared steps at the bottom. Every route ends the same way.

theme v4.4.1 jarvis-modules v2.3.2 Canvas pin 1.8.0 released 2026-11-24

Before anything

Back the database up first. drush cr on a 3.x → 4.x jump runs one-way content migrations — Sections become 1 Column, variant props get renamed, saved component trees are rewritten in place. There is no down path except a restore.

# DDEV
ddev snapshot --name pre-jarvis-4.4.1

# anywhere else
mkdir -p ~/backups
drush sql:dump --gzip --extra-dump='--no-tablespaces' \
  --result-file=~/backups/pre-jarvis-4.4.1.sql

Two things bite on shared hosting, both seen on dev.littlemiamistatepark.org (cPanel) on 2026-11-20. Drush will not create ~/backups for you — without the mkdir you get mysqldump: Got errno 11 on write. And the database user there lacks the PROCESS privilege, so mysqldump aborts with "you need (at least one of) the PROCESS privilege(s)" before writing a byte; --extra-dump='--no-tablespaces' is the fix. Note the filename has no .gz — --gzip appends it, and passing it yourself produces .sql.gz.gz.

Prove the dump is complete before you touch anything. A truncated dump is not a rollback:

gunzip -c ~/backups/pre-jarvis-4.4.1.sql.gz | tail -2   # must end: -- Dump completed on ...

Never re-run the recipe to upgrade. recipes/jarvis and jarvis-install-recipe are install-only. Re-applying one on a live site fails on config that already exists, and in the worst case overwrites configuration you have since changed by hand.

Pin Canvas before touching the theme, on every route. The recipe's constraint is ^1.8, which happily resolves to 1.9+ — and 1.9.0 breaks the link-autocomplete patch mid-install. Nail it down first, so nothing drags it along:

composer require 'drupal/canvas:1.8.0' 'drupal/canvas_ai:1.8.0' --no-update

That writes the pin into composer.json without resolving anything yet. Skip this on a folder-copy site, which has no composer-managed Canvas.

A Canvas already above 1.8 is not a reason to downgrade it. Jarvis 4.4.1 still declares drupal/canvas: ^1.8, and the theme has been seen rendering correctly well above that floor: 4.3.3 on Canvas 1.13.0 (dev.littlemiamistatepark.org, 2026-11-20 — hero, stat row, cards, views block, nav, no console errors), and 4.4.1 on Canvas 1.12.0 (reference checkout, 2026-11-24). Pin whatever is installed so nothing moves underneath you; do not drag it back to 1.8.

Every upgrade: can the field_display workaround come out yet? jarvis_canvas carries an interim fix, JarvisCanvasHooks::configSchemaInfoAlter(), for a canvas_field_component bug that crashes on Canvas 1.13+ (see Known breakages). It is meant to be removed as soon as canvas_field_component ships its own fix. Check on every Jarvis, Canvas or canvas_field_component upgrade:

  1. Look at the upstream issue in the canvas_field_component issue queue ("ConfigSchemaHooks appends 'field_display' as a positional element to the Choice constraint", reported by Andrii) and the module's release notes. Is it closed and in a tagged release?
  2. Confirm it in the code you are about to install. A fixed release mentions choices in its alter; the broken 1.0.2 does not: 
    grep -n "choices" web/modules/contrib/canvas_field_component/src/Hook/ConfigSchemaHooks.php
# no output  = still broken, keep the Jarvis hook
# any output = fixed upstream, the Jarvis hook can go
  3. If it is fixed: raise the drupal/canvas_field_component constraint to that release, delete configSchemaInfoAlter() and its ReorderHook / OrderAfter imports from jarvis_canvas/src/Hook/JarvisCanvasHooks.php, run the validation check under Known breakages, and delete this box.

Leaving the hook in after upstream is fixed is harmless (it does nothing then), so there is no rush, but do not let it linger.

Which route is this site on?

Ask the site, not your memory — one of these has been wrong before. Run these in the composer root:

{ composer show imrodmartin/jarvis 2>/dev/null || composer show drupal/jarvis 2>/dev/null; } \
  | grep -E '^(name|versions|path)' || echo 'not a composer package'

ls -d web/themes/*/jarvis themes/*/jarvis 2>/dev/null

git -C web/themes/custom/jarvis rev-parse --short HEAD 2>/dev/null \
  || echo 'theme dir is not a git repo'
What you seeRoute
composer show prints a version and a pathA — Composer. If name reads drupal/jarvis, do the one-time rename in step 2.
Not a composer package, but the theme dir is a git repo, and .gitmodules lists itB — Git submodule
Not a composer package, theme dir is not a git repo — just filesC — Folder copy / deploy script

Check the version string too, and do not trust it alone. A site can report version: '1.1' in jarvis.info.yml while actually running a feature branch from months later — that exact case cost a full debugging cycle on 2026-11-20. The composer show / git rev-parse output above is the truth; the info.yml version is a label someone forgot to bump.

Route A — Composer

AComposer-managed theme

The normal case. drupalhelps.com is one of these: project root /home/dh, docroot public_html, theme at themes/contrib/jarvis, so drush needs --root.

1. Repositories: Packagist, or the two VCS repos

Jarvis is not on drupal.org, but from theme 4.5.0 the theme (imrodmartin/jarvis) and imrodmartin/jarvis-modules are on Packagist, which every composer project already searches. Nothing to add on a normal host. Sites set up earlier have these two VCS entries, and they can stay; a host that cannot reach Packagist needs them:

composer config repositories.jarvis vcs https://github.com/imrodmartin/jarvis
composer config repositories.jarvis-modules vcs https://github.com/imrodmartin/jarvis-modules

2. Pin Canvas, then upgrade the theme and module

composer require 'drupal/canvas:1.8.0' 'drupal/canvas_ai:1.8.0' --no-update
composer require 'imrodmartin/jarvis:^4.5' 'imrodmartin/jarvis-modules:^2.3'

The theme requires jarvis-modules ^2.3 itself, so naming the module is belt-and-braces — but it guarantees you do not end up with a new theme against an old module.

One time per site: the package was renamed in 4.5.0. Up to 4.4.4 the theme was drupal/jarvis. Packagist does not accept the drupal/ vendor, so it is now imrodmartin/jarvis, with "replace": {"drupal/jarvis": "self.version"}. That keeps old recipe tags working, but not your own root composer.json, which still names drupal/jarvis because recipe unpacking copied it there. Drop the old name before the require above:

composer remove drupal/jarvis --no-update

Skip it and the require stops with found drupal/jarvis[v4.4.x] in the lock file but not in remote repositories. Composer takes a GitHub repository's package name from its default branch, so once that branch says imrodmartin/jarvis the old name is gone everywhere. The theme stays in themes/contrib/jarvis with the same machine name; Drupal only sees a normal update. If the site's extra.installer-paths names "drupal/jarvis", change it to "imrodmartin/jarvis" first or the theme moves directories.

Never pass -W / --with-dependencies. It churns Canvas and undoes the scripts/fix-canvas-autocomplete.php patch. Name the packages you mean, every time.

3. Shared steps

Continue at After every route.

On drupalhelps specifically: drush is vendor/bin/drush --root=public_html, and the host runs with shell_exec disabled and no fileinfo, which makes ai_automators throw 500s on file/image field config forms. That is a pre-existing host condition, not something the upgrade caused.

Route B — Git submodule

BTheme as a git submodule

The reference checkout works this way: the theme lives at web/themes/custom/jarvis as a submodule, and jarvis_canvas is a tracked directory or a second clone under web/modules/custom.

composer update drupal/jarvis does nothing here. It prints Package "drupal/jarvis" listed for update is not locked and moves on — while still churning Canvas. Use git.

1. Pin Canvas (same as route A)

composer require 'drupal/canvas:1.8.0' 'drupal/canvas_ai:1.8.0' --no-update
composer update drupal/canvas drupal/canvas_ai

2. Move the submodule to the release tag

git -C web/themes/custom/jarvis fetch --tags
git -C web/themes/custom/jarvis checkout v4.4.1
git add web/themes/custom/jarvis
git commit -m 'Pin the theme submodule to the released v4.4.1'

Checking out the tag is better than git submodule update --remote, which follows the branch tip and can land you on unreleased work — which is how a site ended up on a four-month-old feature branch.

3. Update the module alongside it

# if web/modules/custom is a clone of jarvis-modules
git -C web/modules/custom fetch --tags && git -C web/modules/custom checkout v2.3.2

If this is the repo that ships the recipe, a submodule bump also needs the recipe's Canvas component config re-exported in the same commit, or fresh installs break at recipe step 5/7 while every existing site keeps working. Use scripts/reexport-components.php; recipes/jarvis/export.sh does not cover it (that exports demo content only).

Export only what actually moved, and prove which that is — capture every component's active_version before the rebuild and again after, then diff the two lists:

drush ev 'foreach (\Drupal::configFactory()->listAll("canvas.component.sdc.jarvis.") as $n) {
  printf("%s %s\n", $n, \Drupal::config($n)->get("active_version")); }' | sort

For 4.3.3 → 4.4.0 that was five components — the five column layouts — and not Text, whose align prop gained only a description in 4.4.0; a description does not enter the version hash, the same way a label does not. Two more things worth knowing before you read the diff: if every shipped file's active_version matches the site before the rebuild, that site is a valid baseline for the branch you are exporting for, whatever branch its checkout happens to sit on. And match each file's existing YAML style rather than one exporter's — the shipped files are mixed, so writing one rendering everywhere produced hundreds of lines of churn with no semantic change. Compare by parsing both sides, not by reading the diff.

Route C — Folder copy / deploy script

CPlain files on the server

No composer package, no git — the theme is a directory someone copied up, by rsync, scp, or a deploy.sh. battle.drtr.site is this: ssh drtr, root ~/battle.drtr.site, docroot web, theme at web/themes/custom/jarvis, module at web/modules/custom/jarvis_canvas.

So is dev.littlemiamistatepark.org: cPanel host, ssh entry nti-littlemiamistate, docroot public_html (so drush is vendor/bin/drush --root=public_html), same two directories. Unlike battle it carries no local patches at all — which is the point of the next block. Do not assume a folder-copy site is patched, and do not assume it is clean. Measure.

Check for local patches before you overwrite anything. battle carries four changes that are deliberately not upstream — a two-column phone_order prop used by five live pages, jarvis_logo_width, the branding block lifted out of the drawer, and a phone gutter rule. A plain swap deletes the prop that published content depends on, and those pages break.

# on the server: what is actually different from the tag it came from?
cd ~/battle.drtr.site/web/themes/custom/jarvis
diff -ru /tmp/jarvis-v4.1.0 . | head -100

That assumes you already know which tag it came from. Usually you do not — there is no composer entry and no git metadata to read, and jarvis.info.yml is only a label. Sweep every tag and let the diff counts tell you. Lowest count is the baseline; a count of 0 means an untouched copy and a safe swap:

git clone --quiet https://github.com/imrodmartin/jarvis /tmp/jarvis-ref
for t in $(git -C /tmp/jarvis-ref tag); do
  git -C /tmp/jarvis-ref checkout --quiet $t
  echo "$t: $(diff -rq --exclude=.git /tmp/jarvis-ref web/themes/custom/jarvis 2>/dev/null | wc -l) differing"
done

Run the same sweep against imrodmartin/jarvis-modules for web/modules/custom/jarvis_canvas, which has no version key in its info.yml at all on a folder-copy site. On littlemiami this returned theme v3.4.0: 0 differing and module v2.1.3: 0 differing — both pristine, so the upgrade became a plain rsync with no patch to re-merge. Once you have the baseline, diff -ru against it is the local patch.

1. Back up both directories on the server

cd ~/battle.drtr.site
mkdir -p ~/backups/jarvis-4.4.1-$(date +%F)
tar czf ~/backups/jarvis-4.4.1-$(date +%F)/theme-before.tgz web/themes/custom/jarvis
tar czf ~/backups/jarvis-4.4.1-$(date +%F)/module-before.tgz web/modules/custom/jarvis_canvas
vendor/bin/drush sql:dump --gzip --extra-dump='--no-tablespaces' \
  --result-file=~/backups/jarvis-4.4.1-$(date +%F)/db.sql

2. Build the new theme locally, patches re-merged

Do not hand-edit the server copy. Produce the exact tree you want, then ship it:

# laptop, in a clone of imrodmartin/jarvis
git fetch --tags
git checkout -b battle-4.4.1 v4.4.1
git apply ~/backups/jarvis-4.1-2026-11-14/battle.patch   # expect conflicts in jarvis.theme
# resolve, then regenerate the patch for next time
git diff v4.4.1 > ~/backups/battle-4.4.1.patch

3. Ship the directories

rsync -av --delete ./ drtr:~/battle.drtr.site/web/themes/custom/jarvis/
rsync -av --delete ~/src/jarvis-modules/jarvis_canvas/ \
  drtr:~/battle.drtr.site/web/modules/custom/jarvis_canvas/

--delete matters: files removed upstream must go, or a stale template keeps winning over the new one.

Then check Canvas's auto-save drafts. The module's migrations rewrite saved component trees but not unsaved editor drafts, and a draft still holding sdc.jarvis.section makes the editor 500 with "Call to a member function requiresExplicitInput() on null". After a 4.x upgrade:

vendor/bin/drush php:eval 'print_r(array_keys(\Drupal::keyValue("canvas.auto_save")->getAll()));'

After every route

drush cr          # THIS is the registration step — it discovers and enables new components
drush updb -y     # module update hooks, including the content-block backfill
drush cr

On a 3.x → 4.x jump the first cr prints the migrations as it runs them, e.g.:

[notice] Converted 16 Section component(s) to 1 Column.
[notice] Renamed the variant prop on 50 Button, Card and Person component(s).
[notice] Converted 12 component(s) in unsaved Canvas drafts to the Jarvis 4.0 shapes.

There is no manual enabling step for components. drush cr auto-enables newly discovered SDCs. If routes 404 right after an upgrade, it is the stale router cache — that cr is the fix.

Verify

# 24 SDC components, all enabled
drush php:eval '$c = \Drupal::entityTypeManager()->getStorage("component")->loadMultiple();
$s = array_filter($c, fn($x) => str_starts_with($x->id(), "sdc.jarvis."));
printf("sdc.jarvis: %d (enabled %d)\n", count($s), count(array_filter($s, fn($x) => $x->status())));'

# content blocks and views blocks should now be enabled (4.4.1 / modules 2.3.0+)
drush php:eval '$c = \Drupal::entityTypeManager()->getStorage("component")->loadMultiple();
foreach ($c as $id => $x) { $l = (string) $x->get("source_local_id");
  if (str_starts_with($l, "block_content:") || str_starts_with($l, "views_block:"))
    printf("%-9s %s\n", $x->status() ? "ENABLED" : "disabled", $id); }'

drush core:status --fields=drupal-version,theme
drush watchdog:show --count=20 --severity=Error

Then open the site and look at it. Component admin lives under Appearance, not Configuration: /admin/appearance/component and /admin/appearance/component/status. The status page lists anything Canvas refused, with reasons.

Known breakages, and what to do

"Missing or invalid module: jarvis_blocks"

Hits any site coming from jarvis-modules 1.x. jarvis_blocks was retired in 2.x, so its files vanish while core.extension still lists it.

Do not drush pm:uninstall jarvis_blocks. Five in-use block types — card, hero, image, text, video — carry dependencies.enforced.module: [jarvis_blocks], so a real uninstall deletes those block types and the blocks your editors built with them.

Repair it instead: drop the enforced dependency first, then remove the module from the installed list.

drush php:eval 'foreach (["card","hero","image","text","video"] as $t) {
  $c = \Drupal::configFactory()->getEditable("block_content.type.$t");
  $d = $c->get("dependencies") ?: []; unset($d["enforced"]);
  $c->set("dependencies", $d)->save(); echo "cleared $t\n"; }
$e = \Drupal::configFactory()->getEditable("core.extension");
$m = $e->get("module"); unset($m["jarvis_blocks"]); $e->set("module", $m)->save();
\Drupal::keyValue("system.schema")->delete("jarvis_blocks");
echo "jarvis_blocks removed\n";'
drush cr

"Cannot use positional argument after named argument during unpacking"

Hits any site on Canvas 1.13+ with canvas_field_component 1.0.2 (or 1.0.x-dev before the upstream fix). Every canvas.component.* config entity fails validation, so a recipe apply or drush cim stops with this error, and Canvas's health check logs it to /admin/reports/dblog on every cron run. The trace ends in ConstraintFactory->createInstance().

Cause: Canvas 1.13 changed the source Choice constraint to the named form Choice: {choices: [...]}, and canvas_field_component still appends field_display beside choices instead of inside it. Reported upstream by Andrii in the canvas_field_component issue queue.

Fix: update jarvis_canvas to the jarvis-modules release after 2.3.2. Its configSchemaInfoAlter() runs after canvas_field_component and moves field_display inside choices. It does nothing on Canvas 1.12 and older. Then drush cr and check that nothing fails:

drush php:eval '$f = \Drupal::configFactory(); $t = \Drupal::service("config.typed"); $bad = 0;
foreach ($f->listAll("canvas.component.") as $n) {
  try { $t->createFromNameAndData($n, $f->get($n)->getRawData())->validate(); }
  catch (\Throwable $e) { $bad++; echo "$n: {$e->getMessage()}\n"; } }
echo $bad ? "$bad failing\n" : "all canvas.component.* config validates\n";'

This is a stopgap. See the check at the top: remove the hook once canvas_field_component releases its own fix.

New props do not appear on sections already on the page

Expected, not a bug. Canvas pins each placed component to the schema version it was saved with, so an existing section keeps rendering its old shape until you re-place it. New components show up immediately; new props on old placements do not. Leave them — they render fine pinned.

This is what 4.4.0 looks like on a site with pages already built. The alignment selects arrive on columns placed from now on; a column placed before the upgrade stays on its retained previous version, renders exactly as it did, and offers no alignment control until it is re-placed. Nothing moves on its own, which is the safe half — but tell editors that, or someone will report the new feature as missing. Converting old placements in bulk means a components_component_version migration, not an update hook.

A hand-deployed module fix gets wiped

Composer replaces web/modules/custom/jarvis-modules/jarvis_canvas wholesale. Any unreleased patch you copied in by hand is gone after an upgrade; re-apply it, or get it released.

What 4.4.0 and 4.4.1 change for editors

ChangeWhat they will notice
Content blocks and views blocks are placeable
modules 2.3.0		 Every reusable content block appears in the Canvas library under its own name, as do views blocks. drush updb enables the ones the site already had. This is the answer to "the same panel on five pages" — build it once, place it, or put it in a region tree for site-wide.
Deleting a block cleans up after itself
modules 2.3.1 / 2.3.2		 A deleted content block used to leave a dead entry in the component library, which errored when placed; so did deleting a View, or removing a block display from one. All three are now cleaned up — the component is removed, or disabled if something still points at it, so a page region or content template is not dragged down with it.
The vertical padding toggle works on coloured sections
theme 4.3.3		 Unticking it used to do nothing on a section with a background — and on a site with a base font above 15px, ticking it actually reduced the padding. Now off means 0 and on means 30px. A coloured section already saved with the toggle off loses 2rem of padding, so look at pages that use one before telling anyone you are done.
Columns align their own content
theme 4.4.0		 The five column layouts — 1/2/3/4 Column and 3 Columns (custom widths) — each gain one alignment setting per column, Left / Center / Right, default Left. A button or heading dropped into a column could only sit left before this. Two knock-ons worth saying out loud: a Text component set to Left now follows its column instead of forcing left (Center and Right still override it), and a WYSIWYG keeps overriding its column, as it always did. Images, maps and video are block-level and full width, so they do not move. The control only appears on columns placed after the upgrade — see New props do not appear on sections already on the page.
A card no longer squashes what sits beside it
theme 4.4.1		 Put a card in a column that already holds something — a WYSIWYG, a heading, a button — and that sibling used to overflow the column with no height reserved for it, so the next section painted straight over it. A card dropped above a hero left the hero's own heading clipped behind the hero image. Cards alone in their column still match heights across a row, which is what that behaviour is for.

The cache rebuild is not optional for this one. Canvas regenerates its versioned component config from the SDC schema during drush cr; without it the five alignment fields never reach the editor tray and the upgrade looks like it did nothing. On a site that exports config, those five canvas.component.sdc.jarvis.* entities come back with a new active_version and need exporting.

Rollback

# database
ddev snapshot restore pre-jarvis-4.4.1           # DDEV
drush sql:drop -y && gunzip -c ~/backups/pre-jarvis-4.4.1.sql.gz | drush sql:cli

# files
composer require 'imrodmartin/jarvis:4.4.1' 'imrodmartin/jarvis-modules:2.3.2'   # route A (needs the jarvis VCS repo)
git -C web/themes/custom/jarvis checkout v4.4.0                             # route B
tar xzf ~/backups/.../theme-before.tgz -C ~/battle.drtr.site                # route C
drush cr

Route A rollback past the rename. Releases before 4.5.0 are not on Packagist (it skips tags whose composer.json still says drupal/jarvis). Through the VCS repo every tag is listed under the new name, so imrodmartin/jarvis:4.4.1 resolves only on a site that kept the repositories.jarvis entry. Add it back first if it is gone (step 1).

Files roll back cleanly. The database does not — the 4.x migrations rewrote component trees in place, so an old theme against a migrated database is not a state that was ever tested. Restore both together or neither.

Three routes is two too many. Route A is the one worth standardising on: it carries the module dependency for you, it pins, and it is the only one where composer show tells you the truth about what is installed. Route C exists on battle only because of local patches — those could ship as a tiny sub-theme instead, at which point battle becomes a composer site too. littlemiami has no such excuse: it is a clean copy, so it is the cheapest site to convert. The one catch is that the composer package installs to themes/contrib/jarvis, so themes/custom/jarvis has to be deleted in the same step — two directories claiming the jarvis machine name is its own kind of afternoon.
